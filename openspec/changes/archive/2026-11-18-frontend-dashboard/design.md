# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/`. Ниже только то, что влияет на реализацию.

- `frontend/` существует, но пуст (0 файлов) — проект создаётся с нуля.
- Backend работает и его контракт зафиксирован спеками `user-auth` и `learning-materials`. Он не умеет: отдавать файлы, извлекать текст, генерировать вопросы, принимать попытки. Поэтому единственный настоящий контент клиента — список материалов.
- CORS на backend уже разрешает `http://localhost:3000` и `http://127.0.0.1:3000`, изменения на стороне API не нужны.
- Окружение: Node.js 22.23.2, npm 10.9.8, pnpm не установлен. Актуальные версии в реестре: `next` 16.4.6, `tailwindcss` 4.3.5.
- Запуск backend и frontend — два отдельных процесса на разных портах.

## Goals / Non-Goals

**Goals:**

- Клиент, который можно открыть в браузере и пройти сценарий «регистрация → вход → загрузка → список» без `/docs`.
- Каркас, в который тесты и результаты лягут добавлением блоков, а не переделкой навигации.
- Единая точка работы с API и с сессией, чтобы новые экраны не повторяли эту логику.

**Non-Goals:**

- Серверная авторизация, middleware, httpOnly-cookie — требуют изменений в backend.
- Предпросмотр, скачивание и удаление материалов — API этого не умеет.
- Стилистический полиш, тёмная тема, мобильная адаптация сверх стандартных брейкпоинтов Tailwind.
- Автоматические тесты фронтенда и сквозные браузерные тесты.

## Decisions

### Клиентские компоненты вместо SSR-авторизации

Все защищённые экраны — клиентские компоненты; серверный рендеринг с токеном не используется.

**Почему:** токен хранится в `localStorage`, а он недоступен серверу. Любой SSR-защищённый роут потребовал бы cookie и, значит, изменений в backend (`/auth/login` должен ставить httpOnly-cookie). Для третьей страницы приложения это несоразмерно.

**Альтернатива:** httpOnly-cookie + `middleware.ts` — безопаснее против XSS и даёт настоящую защиту на сервере. Отложено до того момента, когда появится что защищать кроме списка файлов; тогда меняются `token.ts` и логин на бэкенде.

**Цена:** первый рендер показывает индикатор загрузки, а не готовый контент; SEO отсутствует (для закрытого приложения не нужен).

### Три маршрута, дашборд как главная

`/`, `/login`, `/register`. Отдельного `/materials` нет: дашборд содержит блок материалов целиком — счётчик, список и форму загрузки.

**Почему:** при одной доменной сущности список и главная неразличимы, а два почти одинаковых экрана заставляют пользователя ходить по кругу. Когда на главной появятся настоящие агрегаты (последний результат, «продолжить тест»), блок материалов сожмётся до трёх строк со ссылкой «все» — это правка одного компонента, а не переделка маршрутов.

**Альтернатива:** `/` как короткая сводка и `/materials` как рабочий экран. Станет уместной позже, когда агрегатов станет больше, чем списка.

### Учётная запись без полного имени

`full_name` удаляется из модели, схемы и ответов API; идентичность пользователя — только логин.

**Почему:** отдельного экрана профиля нет, а поле «имя и фамилия» при регистрации заставляло вводить данные, которые нигде не отображаются. В интерфейсе это была единственная причина показывать ФИО в шапке — логин справляется с той же задачей.

**Цена:** удаление колонки через `create_all` невозможно, базу нужно пересоздать — данные тестовые. Заодно это внешняя ломка контракта: старый клиент, присылающий `full_name`, получит `422`, поэтому изменение помечено BREAKING в proposal.

**Альтернатива:** оставить колонку, но не спрашивать поле и писать в него логин — оставляет в схеме поле-двойник и враньё в спеке.

### Единый API-клиент

`src/lib/api.ts` — тонкая обёртка над `fetch`: базовый URL из `NEXT_PUBLIC_API_URL`, автоматический `Authorization: Bearer`, разбор тела ошибки, вызов общего обработчика `401`.

**Почему:** FastAPI возвращает `detail` то строкой, то массивом (у `422` массив ошибок валидации). Разбирать эту форму в каждом компоненте — гарантированные расхождения в текстах. Обработчик `401` в одном месте исключает ситуацию «на одном экране токен сбросили, на другом нет».

**Альтернатива:** `axios` с интерсепторами — лишняя зависимость ради того, что `fetch` делает в 30 строках.

### Токен за отдельным модулем

`src/lib/token.ts` с `getToken` / `setToken` / `clearToken` поверх `localStorage`.

**Почему:** при переезде на httpOnly-cookie меняется один файл и вызывающий код остаётся прежним. Обращение к `localStorage` напрямую по компонентам сделало бы этот переезд поиском по всему проекту.

### Защита маршрута в хуке, а не в middleware

`useSession()` на клиенте: нет токена → `router.replace('/login')`.

**Почему:** `middleware.ts` в Next.js не имеет доступа к `localStorage` — проверять там нечего. Логика, размазанная по страницам, дублировалась бы в каждом новом экране.

### Явные состояния загрузки

Каждый блок работает с состоянием `loading | error | ready`, а не с «массив пустой → значит пусто».

**Почему:** иначе при каждом открытии дашборда на долю секунды показывается «Материалов пока нет», хотя материалы есть. Это одна из тех мелочей, которые сильнее всего портят впечатление от MVP.

### Валидация форм: только обязательные поля

Клиент проверяет непустые поля и расширение файла; всё остальное (длина пароля 8–72, допустимые символы `username`, лимит размера) решает backend и возвращает код, который клиент переводит в текст.

**Почему:** дублировать правила из `schemas/user.py` на клиенте — значит держать две копии, которые разъедутся. Сообщения API стабильны по кодам (`401`, `409`, `413`, `415`, `422`), а не по текстам.

**Ограничение:** пользователь узнаёт о требовании к паролю после отправки. Приемлемо для MVP; при желании подсказка добавляется текстом под полем, без дублирования логики.

### Ошибки API переводятся по коду

Таблица соответствий в одном месте:

| Код | Что видит пользователь |
|---|---|
| `401` | «Неверное имя или пароль», сброс сессии на защищённых экранах |
| `409` | «Такое имя уже занято» |
| `413` | «Файл больше 20 МБ» |
| `415` | «Поддерживаются только PDF, DOCX и PPTX» |
| `422` | первое сообщение валидации из `detail` |
| иное | «Не удалось выполнить запрос, попробуйте ещё раз» |

**Почему:** интерфейс на русском, а тексты FastAPI английские и технические. Коды — часть контракта, тексты — нет.

### shadcn/ui с зафиксированным фолбэком

Инициализация через `npx shadcn@latest init`, затем `add button input card label`. Если CLI не совместим с Next 16 / Tailwind 4, компоненты вендорятся вручную в `src/components/ui/` вместе с утилитой `cn()` (`clsx` + `tailwind-merge`).

**Почему:** `AGENTS.md` требует shadcn/ui, и нормальная инициализация даёт `components.json`, по которому следующие компоненты добавляются одной командой. Но версии свежие, и упереться в несовместимость CLI на середине задачи — реальный риск; ручной вариант даёт те же четыре компонента, потому что это обычные Tailwind-обёртки.

### Tailwind 4 в CSS-first режиме

`@import "tailwindcss"` в `globals.css`, без `tailwind.config.ts` и без `postcss.config.js` сверх того, что создаёт установщик.

**Почему:** в Tailwind 4 конфигурация живёт в CSS; попытка завести старый конфиг на этом стеке добавляет путаницу, а не возможности.

### Загрузка файла через FormData и fetch

`POST /materials` вызывается из обработчика формы с `FormData`, а не нативной отправкой формы.

**Почему:** нативная отправка не даёт добавить `Authorization` и не позволяет разобрать `413`/`415` в интерфейсе.

### Автоматический вход после регистрации

`POST /auth/register`, затем сразу `POST /auth/login` с теми же данными.

**Почему:** `/auth/register` не возвращает токен, а менять контракт backend ради экономии одного запроса — несоразмерно. Два последовательных вызова дают пользователю ожидаемое «зарегистрировался и уже внутри».

### Даты через `Intl`, без библиотек

`new Intl.DateTimeFormat('ru-RU', { day: '2-digit', month: '2-digit', year: 'numeric' })`.

**Почему:** одна функция вместо `date-fns`/`dayjs`; формат `18.11.2026` читается и не зависит от локали браузера.

## Risks / Trade-offs

- **Токен в `localStorage` уязвим к XSS** → снимается переездом на httpOnly-cookie вместе с изменением `/auth/login`; пока приложение не рендерит чужой HTML, риск ограничен.
- **Свежие версии Next 16 / Tailwind 4 / shadcn CLI** → фолбэк на ручное добавление четырёх компонентов описан выше; если не заведётся и это, проблема будет в самом Next, и тогда фиксируется версия ниже.
- **Первый рендер мигает индикатором** из-за клиентской проверки токена → лечится явным состоянием `loading`, а не скрытием контента.
- **Нет автоматических тестов** → сценарии из `specs/` — ручной чек-лист; при добавлении `playwright` они превращаются в тесты почти дословно.
- **`NEXT_PUBLIC_API_URL` попадает в клиентский бандл** → это адрес, а не секрет; настоящих секретов у фронтенда нет и быть не должно.
- **CORS настроен только на localhost** → при выкладке понадобится добавить домен в `CORS_ORIGINS` на backend; сейчас не блокирует.
- **Установка npm в песочнице агента требует переноса кэша в рабочую папку** (иначе `EPERM`), к пользователю это не относится — у него npm работает штатно.

## Migration Plan

Проект новый, миграции данных не нужны.

1. `cd frontend`
2. `npm install`
3. создать `.env.local` с `NEXT_PUBLIC_API_URL=http://127.0.0.1:8000`
4. `npm run dev` → `http://localhost:3000`

Перед первым запуском backend нужно пересоздать базу: `full_name` удаляется из модели, а `create_all` не умеет удалять колонки.

```bash
cd backend
del studymate.db
uv run python -m app.main
```

Backend должен быть запущен отдельно (`uv run python -m app.main` в `backend/`).

Откат: удалить содержимое `frontend/`, вернуть две строки в `.gitignore` и раздел README. На backend change не влияет.

## Open Questions

- **Карточка материала.** Когда появится генерация тестов, понадобится `/materials/[id]`. Сейчас ссылок на неё нет; решать вместе с той функциональностью.
- **Размер файла в списке.** API его не возвращает, поэтому показать нечего. Либо добавить поле в `MaterialRead`, либо не показывать вовсе — вопрос к следующему изменению backend.
