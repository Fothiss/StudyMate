# Design

## Context

See `proposal.md` → Why для мотивации. Здесь только то, что определяет подход.

Текущее состояние, важное для решений:

- `frontend/` — Next.js 16.4 (App Router, `cacheComponents: true`, `partialPrefetching: true`) с Turbopack-правилом, подключающим Tailwind через `@tailwindcss/turbopack`. Все четыре файла страниц начинаются с `"use client"`. SSR, `next/image` и route handlers не используются нигде.
- Токен доступа лежит в `localStorage` (`src/lib/token.ts`), поэтому серверный рендер не видит сессию и защита маршрута всё равно выполняется после монтирования.
- shadcn настроен на стиль `base-nova` с `@base-ui/react` и импортом `cn` из пакета `cn`; `components.json` ссылается на `src/app/globals.css`, который начинается с `@import "shadcn/tailwind.css"`.
- Палитра — стоковый neutral: `--primary: oklch(0.205 0 0)`, ни одного хроматического токена.
- Backend: `POST /materials/{id}/quiz` без тела, схема `Quiz{summary, questions[{text, options, correct_index}]}`, промпт жёстко задаёт «5 вопросов, ровно 4 варианта», клиент GigaChat — `lru_cache`-синглтон с `with_structured_output(Quiz)`.
- Замеры из предыдущего change: ответ модели по 15-страничному PDF занимает 37–67 с, `verify_ssl_certs` локально выключен, потоков у физлица один.

## Goals / Non-Goals

**Goals:**

- Снять зависимость от Next.js без потери маршрутов и без сервера Node для раздачи статики.
- Задать дизайн-систему как набор токенов, а не набор покрашенных классов: две темы, градиент, стекло, шкала радиусов и теней.
- Держать одинаковое поведение для тёмной и светлой темы, проверяя контраст по токенам, а не по каждому экрану.
- Сделать прохождение теста возможным без сохранения данных на сервере.
- Сохранить `material-quiz` транзитивной: ни тест, ни ответы, ни оценка не пишутся в БД.

**Non-Goals:**

- Роли, назначения и кабинет преподавателя — они потребуют серверной проверки и хранения попыток, то есть другой архитектуры.
- История результатов, прогресс, графики: раздел «Результаты» остаётся заглушкой.
- Замена UI-кита: `shadcn`/`@base-ui/react` остаются, меняется только оформление и добавляются недостающие примитивы.
- Кэширование сгенерированных тестов на сервере, фоновые задачи, стриминг ответа модели.

## Decisions

### 1. Vite + React Router вместо Next.js

Приложение целиком клиентское, поэтому переезд не требует переносить логику: `src/lib/api.ts`, `src/hooks/use-session.ts` и все компоненты остаются, меняются только точка входа, роутинг и оболочка.

```
frontend/
  index.html                 <- статический шаблон, сюда же inline-скрипт темы
  vite.config.ts             <- react + @tailwindcss/vite + alias "@" -> src
  src/
    main.tsx                 <- createRoot + RouterProvider
    app/router.tsx           <- маршруты и layout-маршруты
    app/require-auth.tsx     <- защита маршрутов вместо useEffect в каждой странице
    app/shell/*              <- сайдбар, переключатель темы, контентная область
    pages/overview/
    pages/practice/
    pages/login/
    pages/register/
    styles/aurora.css        <- токены, темы, keyframes
  components/                <- существующие + quiz/* и ui/*
```

| Критерий | Next.js | Vite |
|---|---|---|
| статика | нужен Node (`next start`) | `dist/` на любом хостинге |
| dev-старт | секунды + экспериментальные флаги | доли секунды |
| `"use client"` | нужен в каждом файле | не существует |
| шрифты | `next/font` | self-hosted `@fontsource-variable/*` |
| роутинг | файловый App Router | `<BrowserRouter>` + `<Routes>` |

Роутинг не переводится на data router с `loader`: данные приходят с токеном из `localStorage`, то есть loaders всё равно клиентские, а `useEffect`-загрузка уже написана и работает. Меньше новых сущностей.

Защита маршрута переезжает из `useSession` в layout-маршрут `RequireAuth` (проверка токена, `<Navigate to="/login" replace/>`). Так защита не дублируется на каждой странице, а `useSession` остаётся только ради `signOut` и обработчика `401`.

`next/font` заменяется на `@fontsource-variable/manrope` и `@fontsource-variable/inter` с явным подключением latin+cyrillic подмножеств: интерфейс русский, а «модные» шрифты (Space Grotesk, Satoshi) кириллицу не содержат.

### 2. Токены вместо классов: Aurora как слой CSS-переменных

Все цвета — в `oklch` в `:root` (светлая) и `.dark`, форма — в `@theme inline`, как уже принято в `globals.css`. Компоненты остаются на существующих токенах (`bg-card`, `text-muted-foreground`, `ring-border`), поэтому покраска не превращается в правку каждого файла.

```
бренд-градиент   --aurora-1 #7C5CFF  --aurora-2 #C56CFF  --aurora-3 #4CD7F6
поверхности      --surface-solid (непрозрачная, под текстом)
                 --surface-glass (rgba + blur, только навигация/статусы/hero)
семантика        --success (emerald), --warning (amber), --destructive
радиусы          --radius: 0.875rem, шкала уже есть в @theme inline
```

Правило, зафиксированное как часть дизайн-системы: **стекло не используется под длинным текстом**. Список материалов, формулировки вопросов и разбор результата живут на `--surface-solid`. Это не эстетическая прихоть: на тёмном фоне полупрозрачный слой с блюром даёт и низкий контраст, и артефакты при скролле.

Тёмная тема — основная по дизайну, но не по умолчанию: без сохранённого выбора тема берётся из `prefers-color-scheme`, как требует спека. Светлая тема — не инверсия: блобы становятся пастельными, стекло заменяется на белые полупрозрачные панели с той же геометрией.

Переключение — класс `dark` на `<html>` + `localStorage`. Чтобы не было вспышки чужой темы, в `index.html` стоит синхронный inline-скрипт, выставляющий класс до первого пейнта; `useTheme` только читает и меняет.

### 3. Четыре анимации на чистом CSS, без библиотеки анимаций

Список эффектов конечен, поэтому `motion` не нужен: появление со stagger решается `animation-delay`, hover — `transform`/`box-shadow`, дрейф градиента — анимацией `background-position`, прогресс — `width` с `transition`.

Переход между шагами визарда делается через View Transitions API (`document.startViewTransition`) с проверкой наличия — там, где API нет, шаг просто меняется без анимации. Это даёт современный эффект без зависимости и без ручного FLIP.

Все анимации обёрнуты в `@media (prefers-reduced-motion: no-preference)` по принципу «по умолчанию статично» — так не нужно отдельно перечислять выключения. `will-change` не ставится на список, только на три блоба фона.

### 4. Оболочка: постоянный сайдбар, контент перерисовывается

```
+--------+------------------------------------------------------+
|  (*)   |  страница                                            |
| Обзор  |                                                      |
| Тест   |                                                      |
|        |                                                      |
| тема   |                                                      |
| выход  |                                                      |
+--------+------------------------------------------------------+
```

Сайдбар — layout-маршрут, поэтому при переходе между страницами он не размонтируется (это же требует спека «Application Navigation»). На узких экранах он превращается в верхнюю полосу с теми же двумя пунктами.

### 5. `/quiz` — один маршрут с явной машиной состояний

Вложенные URL (`/quiz/new`, `/quiz/run`, `/quiz/result`) не нужны: состояние всё равно клиентское, а `sessionStorage` пришлось бы синхронизировать с адресом. Один маршрут, состояния выражены явно:

```
configuring --generate--> generating --ok--> answering --submit--> submitted
     ^                        |                  |                    |
     |                        v                  |                    v
     +---------------------- error <-------------+               evaluating
     |                                                               |
     +------------------------ evaluationError <--------+--ok---> evaluated
```

Пока идёт `generating`, показывается не спиннер, а фазы с текстом («читаем материал», «составляем вопросы»): запрос реально занимает до минуты, и честный прогресс читается лучше вращающегося круга. Фазы — декоративные, они не претендуют на измерение.

### 6. Состояние прохождения — в `sessionStorage`, с версией

```ts
type StoredPractice = {
  version: 1;
  materialId: string;
  materialTitle: string;
  quiz: Quiz;
  answers: Record<number, number | string>;   // индекс вопроса -> ответ
  submitted: boolean;
  evaluation?: Evaluation;
};
```

Ключ `studymate:practice:v1`. Своя вкладка — своё состояние, что совпадает с ожиданием «новая вкладка начинает с чистого листа». Невалидный JSON или чужая `version` — запись удаляется, страница открывается в `configuring`. Новая генерация перезаписывает запись целиком.

Альтернатива — `localStorage` — отклонена: черновик прохождения через сутки после закрытия вкладки выглядит как сломанное состояние, а не как удобство.

### 7. Схема теста: размеченное объединение, но с планом отката

```python
class ChoiceQuestion(BaseModel):
    kind: Literal["choice"]
    text: str
    options: list[str]                  # min_length=2
    correct_index: int

class OpenQuestion(BaseModel):
    kind: Literal["open"]
    text: str
    reference: str                      # min_length=1

Question = Annotated[ChoiceQuestion | OpenQuestion, Field(discriminator="kind")]
```

Тело запроса генерации: `{choice_count: int, open_count: int}`, ограничения `0 <= choice_count <= 15`, `0 <= open_count <= 10`, `choice_count + open_count >= 1`. Ограничения проверяются в схеме, чтобы отказом занимался FastAPI, а не роут.

Риск: `with_structured_output` в режиме `function_calling` передаёт JSON Schema инструментом, и размеченное объединение — более сложная схема, чем плоский объект. Если GigaChat начнёт возвращать невалидное объединение, откат — два отдельных вызова (вопросы с вариантами и открытые вопросы) с плоскими схемами, склеенные в один `Quiz`. Промпт для открытых вопросов при этом ещё и становится точнее.

### 8. Параметризация промпта безопасна, потому что материал идёт отдельным сообщением

В `prompts/quiz.py` текст инструкции можно собирать f-строкой: материал подставляется как содержимое `HumanMessage`, а не в шаблон, поэтому фигурные скобки из лекции ничего не сломают. Это сохраняет правило из докстринга модуля.

Числа попадают в инструкцию, а не в схему: модель, которой сказали «8 вопросов с вариантами», всё равно может вернуть 7. Принимаем результат как есть и показываем «сгенерировано 7 из 8» — ретрай стоил бы ещё минуты ожидания.

### 9. Проверка тестовых ответов на клиенте — осознанная уступка

`correct_index` приходит в теле генерации, поэтому проверка выполняется в браузере: ноль задержки, ноль дополнительных запросов. Ответы при этом видны в DevTools.

Для сценария «студент готовится сам» это не проблема: он единственный владелец материала и не обманывает никого, кроме себя. Как только появятся назначения от преподавателя, оценивание обязано переехать на сервер — это зафиксировано в Non-Goals и в Risks, чтобы решение не потерялось.

### 10. Оценка открытых ответов: пакетный запрос, эталон присылает клиент

`POST /quiz/check`:

```json
{ "material_id": "...",
  "answers": [ { "question": "...", "reference": "...", "answer": "..." } ] }
```

Ответ: `{ "results": [ { "index": 0, "score": 0..100, "feedback": "..." } ] }`, где `index` — позиция во входном массиве.

Эталон присылает клиент, потому что тест транзитивный и сервер не хранит сгенерированное. Это позволяет подделать эталон, но влияет только на собственную обратную связь студента — приемлемо для тренажёра. Альтернатива — кэш сгенерированных тестов по `quiz_id` — требует состояния на сервере и противоречит требованию Transient Quiz.

Все открытые ответы уходят одним запросом: у физлица один поток, поэтому N последовательных вызовов заняли бы N×минуту. Пустой ответ не отправляется в модель — он сразу получает `score: 0` и короткий комментарий, чтобы не тратить токены.

Оценка 0–100 натуральная и позволяет суммировать с процентом по тестовым вопросам.

### 11. Ошибки модели не должны уничтожать результат

`submitted` фиксируется до запроса оценки. Если проверка открытых упала, экран остаётся результатом: счёт по тестовым вопросам уже посчитан, на месте обратной связи — сообщение и кнопка «проверить снова». Это прямое следствие спеки и одновременно защита от худшего UX: минута генерации и ответы не теряются из-за одного `502`.

## Risks / Trade-offs

- **Размеченное объединение может не пройти через `function_calling`** → план отката из решения 7 (два вызова с плоскими схемами); проверка — живой вызов до того, как страница будет собрана.
- **Два вызова вместо одного** при откате удваивают ожидание (до ~2 мин) → фазы прогресса и `AbortController` с понятным сообщением вместо бесконечного ожидания.
- **Ответы видны в DevTools** → принято для тренажёра (решение 9); при появлении назначений от преподавателя проверка должна переехать на сервер.
- **Клиент присылает эталонные ответы на проверку** → подделка влияет только на свою же обратную связь; альтернатива требует серверного состояния.
- **`sessionStorage` хранит и правильные ответы** → тот же класс риска, что и выше; данные живут до закрытия вкладки.
- **Появление контента в тёмной теме может выглядеть дёшево** → зерно (`feTurbulence`) поверх блобов и запрет стекла под текстом; проверка контраста по токенам, а не на глаз.
- **Вспышка светлой темы при загрузке** → синхронный inline-скрипт в `index.html` до первого пейнта.
- **Шрифт без кириллицы сломает вёрстку** → в задаче зафиксирована явная проверка, что оба подмножества подключены и `document.fonts.check` проходит.
- **Миграция ломает документацию проекта** → `AGENTS.md` и `README.md` обновляются в том же change, до архивации.
- **Один большой change**: `web-dashboard` расходится с кодом между миграцией и появлением `/quiz` → порядок задач такой, что каждый шаг оставляет приложение работоспособным.
- **Удаление Next.js ломает привычку `next dev`** → `package.json` получает только `dev`/`build`/`preview`, README обновляется, `AGENTS.md` описывает новый стек.

## Migration Plan

1. Frontend-миграция выполняется первой и целиком: новый `package.json`, `vite.config.ts`, `index.html`, `main.tsx`, `router.tsx`; страницы переносятся как есть, без изменения разметки. Проверка — приложение открывается, вход работает, материалы загружаются.
2. Backend меняется вторым, но обратно совместимо по кодам: новые поля и валидация появляются вместе, старый клиент не поддерживается (развёрнутых клиентов нет).
3. Спека архивируется после того, как `/quiz` появится: до этого `web-dashboard` описывает будущее состояние.
4. Откат: изменения не трогают БД и файловое хранилище, поэтому откат — возврат файлов; загруженные материалы и пользователи не затрагиваются.
