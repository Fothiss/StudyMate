# Design

## Context

Материалы уже сохраняются на диск (`backend/storage/materials/{id}/{filename}`), в БД есть `materials.extracted_text` и `materials.extraction_status`, но обе колонки пустые и нигде не используются. Эндпоинты `POST /materials`, `GET /materials`, `GET /materials/{id}` работают по спеке `learning-materials`. Зависимостей для AI в backend до этого change не было.

Ключевые ограничения получены замерами на живом GigaChat API (модель `GigaChat-3-Ultra`) на PDF «Attention Is All You Need», 15 страниц:

| Факт | Значение |
|---|---|
| вес PDF в контексте | 13 863 токена |
| вес извлечённого текста (транскрипция GigaChat) | 11 205 токенов (40 375 символов) |
| вес извлечённого текста (`pdfplumber`, `x_tolerance=1`) | 8 635 токенов (39 719 символов) |
| `max_tokens` по умолчанию | 8 192 — 15 страниц уже обрезаются |
| время ответа | 37–67 с |
| потоков у физлица | 1 |

## Goals / Non-Goals

**Goals:**

- Текст материала доступен внутри системы и переиспользуется без повторного чтения файла.
- Генерация вопросов возвращает валидируемую структуру, а не свободный текст.
- Отказ вместо «тихо сохранённого» непригодного материала.

**Non-Goals:**

- OCR сканированных PDF и любые не-PDF форматы.
- Сохранение сгенерированных вопросов, прохождение теста, проверка ответов.
- Фоновые задачи и очередь: генерация синхронная.

## Decisions

### 1. Парсинг локальный, `pdfplumber` вместо GigaChat `attachments`

GigaChat умеет читать документ, приложенный к запросу, но текст наружу не отдаёт — только сгенерированный ответ. Замеры показали три проблемы этого пути:

- с `response_format=json_schema` модель вызывала `text2image` вместо `get_file_content` (воспроизведено);
- с явным `functions=[{"name": "get_file_content"}]` вызов приходил, но ответ обрывался на `finish_reason=function_call` с пустым `content`;
- дословная транскрипция нестабильна: два полных прогона дали 40 375 и 34 992 символа, то есть текст пересказывается, а не копируется.

Локальный парсинг снимает все три: текст доступен и стабилен, `with_structured_output` работает в обычном режиме, токены не тратятся на повторное чтение.

`pdfplumber` выбран против `pypdf`: MIT-лицензия у обоих, но `pdfplumber` разбирает таблицы (`extract_tables`) и точнее восстанавливает порядок в двухколоночной вёрстке — а именно она чаще всего встречается в лекциях. Альтернатива `pypdf` дешевле по зависимостям и быстрее, но таблицы в документации прямо объявлены вне планов. Разница в скорости на 40 страницах — секунды, на фоне 37–67 с ожидания модели несущественна.

`extract_text(layout=True)` не используется: он добивает текст пробелами до сетки и раздувает число токенов. Дополнительно требуется `x_tolerance=1`: значение по умолчанию (3) склеивает слова там, где глифы стоят плотно, и на проверочном PDF вместо «Provided proper attribution» выходило «Providedproperattribution».

### 2. Текст передаётся сообщением, ответ — через `with_structured_output`

Встроенная функция `get_file_content` при текстовом входе не нужна, значит `function_call` можно форсировать. `with_structured_output(Quiz)` в режиме по умолчанию (`function_calling`) привязывает схему как инструмент и парсит ответ `PydanticToolsParser` — без ручного разбора JSON.

`method="json_schema"` не используется: он опирается на `response_format`, а совместимость `response_format` с документами уже показала себя ненадёжной.

### 3. Лимит 30 000 токенов, оценка локальная

`len(text) / 4.6` — та же формула, что внутри `langchain_gigachat` при `use_api_for_tokens=False`. Отдельный вызов `/tokens/count` не нужен: он добавляет сетевой запрос и ничего не меняет при отказе по лимиту.

Лимит проверяется при загрузке, а не в генерации: непригодный материал не попадает в базу. 30 000 токенов — это примерно 52 страницы, исходя из 8 635 токенов на 15 страниц.

### 4. Извлечение синхронно в `POST /materials`

`pdfplumber` разбирает 40 страниц за секунды, очередь и фоновые задачи для этого не нужны. Генерация quiz тоже синхронная: один запрос к модели, 20–60 с. Фоновая задача потребовала бы статусов, опроса и отдельной сессии SQLAlchemy — на прототип этого не нужно.

### 5. Отказ с очисткой вместо статуса `too_big`

При пустом текстовом слое и при превышении лимита загруженный файл удаляется, запись не создаётся. Уже существующий в `create_material` механизм очистки каталога переиспользуется как есть. Альтернатива — хранить материал со статусом `failed` и показывать его в списке — требует поля в API и UI, а ценности не даёт: вопросы по такому материалу всё равно не сгенерировать.

### 6. Схема quiz и её валидация

```
Quiz
  summary: list[str]        # 3-5 пунктов
  questions: list[Question]
    Question
      text: str
      options: list[str]    # 2+ варианта
      correct_index: int    # индекс в options
```

`correct_index` проверяется вручную после парсинга: модель может вернуть индекс вне диапазона, а Pydantic этого не поймает. Невалидный ответ — `502`, без сохранения и без возврата частичного результата.

### 7. Клиент GigaChat — один экземпляр

Конструктор `GigaChat` при каждом создании проходит OAuth. Экземпляр создаётся лениво один раз (`lru_cache`) из настроек `app/core/config.py` и переиспользуется. Промпты лежат в `app/services/prompts/`, отдельно от логики — требование `AGENTS.md`.

### 8. Генерация на дашборде — одна карточка вместо заглушки

Заглушка «Тесты» была честной, пока эндпоинта не существовало; теперь она врёт, поэтому заменяется компонентом `quiz-block.tsx`. Он получает список материалов от страницы, а не загружает их сам: данные уже есть, второй запрос не нужен.

Кнопка на каждый материал выбрана вместо выпадающего списка: в `components/ui/` нет компонента `select`, а добавлять его ради одного места — лишняя зависимость. Значения `variant` у `Button` хватает, чтобы показать выбранный материал.

Верный вариант подсвечивается сразу. Полноценное прохождение теста (ответы, подсчёт, результат) вне scope, а прятать правильный ответ без механики проверки бессмысленно: проверять ответы нечем.

## Risks / Trade-offs

- **Модель может вернуть вопросы не по материалу или меньше запрошенных** → промпт запрещает выходить за текст, структура валидируется, но смысловое качество не проверяется автоматически. Принято для прототипа.
- **30 000 токенов ≈ 52 страницы** → лекция на 60–80 страниц получит `422`. Осознанное ограничение; поднимается одной настройкой, если понадобится.
- **`pdfplumber` теряет формулы и сложные таблицы** → часть материала может дойти до модели в искажённом виде. Проявляется только на практике.
- **`verify_ssl_certs=False` локально** → в `config.py` значение по умолчанию `False`, потому что окружение не доверяет цепочке GigaChat. Для прода нужен `GIGACHAT_CA_BUNDLE_FILE`; отмечено в задачах.
- **Один поток у физлица** → одновременные загрузка и генерация выстраиваются в очередь; таймаут клиента поднят до 120 с, чтобы запрос не обрывался раньше модели.
- **BREAKING для `.docx` и `.pptx`** → существующие загруженные материалы этих форматов остаются в БД, но новые не принимаются. Спека `learning-materials` обновляется этим же change.
- **Верный ответ виден сразу** → это просмотр, а не тест. Прохождение с ответами и результатом — следующий change, тогда подсветку надо будет спрятать.
- **UI не проверен в браузере** → типы и линтер проходят, контракт с API сверен по живому ответу, но нажатия в браузере не выполнялись. Проверка отложена до запуска обоих процессов.

## Migration Plan

- Схема БД не меняется: `extracted_text` и `extraction_status` созданы заранее.
- Существующие записи материалов остаются без текста и не смогут сгенерировать quiz (`422`). Перезалить файл — штатный путь.
- Откат: удалить новые модули и вернуть `ALLOWED_EXTENSIONS` в исходное состояние; колонки остаются пустыми, данные не теряются.
