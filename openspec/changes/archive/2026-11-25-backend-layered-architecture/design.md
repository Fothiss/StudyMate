# Design

## Context

Мотивация — в `proposal.md`. Здесь только то, что влияет на реализацию.

- FastAPI + SQLAlchemy (`Session` на запрос через `get_db` в `app/core/db.py`), Pydantic-схемы отдельно от ORM.
- Хранилище по умолчанию — SQLite (`app/core/config.py`), `Base.metadata.create_all` при старте; миграций нет.
- Сейчас зависимости собираются в `app/api/deps.py`, а `app/services/materials.py` совмещает файловый ввод-вывод, парсинг PDF, SQL и транзакции.
- Тестов в проекте нет; характеризационные тесты перед рефакторингом сознательно отложены.
- `services/gigachat.py` не обращается к БД: он получает текст материала строкой.

## Goals / Non-Goals

**Goals:**

- Единая точка сборки зависимостей вне HTTP-слоя.
- Изоляция доступа к данным: SQL только в репозиториях.
- Одна граница транзакции на операцию, и она в сервисе.
- Роутеры не создают зависимости вручную и не знают о `Session`.
- Внешне наблюдаемое поведение — идентично текущему.

**Non-Goals:**

- Новые таблицы, эндпоинты и поля (это следующий change).
- Замена модулей функций на классы ради симметрии (LLM-клиент, `storage`, `pdf` остаются функциями).
- Тесты, миграции Alembic, переход на PostgreSQL.
- Введение `UnitOfWork`-класса поверх сервисов.

## Decisions

**1. Направление зависимостей: `api → dependencies → services → repositories → models`.**

Сборка выносится в `app/dependencies/`, потому что `api/` должен уметь только HTTP. При альтернативе «оставить `api/deps.py`» слой `api` знает про все репозитории — это и было исходной проблемой.

**2. Сервисы — классы с конструкторным внедрением, а не функции с `db` первым аргументом.**

Сейчас `get_material(db, user, material_id)` жёстко связывает сервис с `Session`. С классом `MaterialService(materials_repo)` зависимость подменяется через `app.dependency_overrides` без monkeypatch. Альтернатива «оставить функции» дешевле, но подмена репозитория потребовала бы правки импортов.

**3. Репозиторий не вызывает `commit`; коммитит только сервис.**

Иначе `create_material` повторится в новом месте: файл, PDF и транзакция снова окажутся в одном `try`. Альтернатива «`repo.commit()`» выглядит короче, но размазывает границу транзакции по слоям, а при нескольких репозиториях в одной операции (нужно для попыток) даёт несколько коммитов вместо одного.

**4. DI — нативное `fastapi.Depends`, без контейнера.**

`Depends` плюс `dependency_overrides` уже дают внедрение и точку подмены. `dependency-injector` или `punq` добавили бы второй механизм рядом с фреймворковым без выигрыша. Тот же аргумент против самописного `ServiceProvider`.

**5. `Annotated`-алиасы: короткие для репозиториев, с суффиксом `Dep` для сервисов.**

`UserRepo = Annotated[UserRepository, Depends(get_user_repo)]`, но `AccountServiceDep` вместо `AccountService` — иначе алиас затеняет имя класса в модуле роутера и ломает импорт типа.

**6. `app/dependencies/__init__.py` остаётся пустым.**

Реэкспорт всего через `__init__` создаёт цикл `services.py ↔ __init__.py`: пакет импортирует подмодуль, который импортирует пакет. Импортировать нужно из конкретного модуля.

**7. Провайдер — одна строка `return X(y)`.**

Любая логика (`if`, чтение настроек, запросы) в провайдере дублирует слой сервиса и делает граф зависимостей непредсказуемым.

**8. LLM-клиент и файловое хранилище в DI не заводятся.**

У `services/gigachat.py` и `services/storage.py` нет зависимостей от БД; провайдеры `get_gigachat_client()` были бы прокладками. Появится необходимость подменять LLM в тестах — тогда и введём.

## Risks / Trade-offs

- **Рефакторинг без тестов может сломать auth/materials/quiz** → компенсируем ручным прогоном девяти обращений (`/health`, `/auth/register`, `/auth/login`, `/users/me`, `POST/GET /materials`, `GET /materials/{id}`, `POST /materials/{id}/quiz`, `POST /quiz/check`) до и после правки со сверкой кодов ответов. Полноценные тесты — следующий change.
- **Репозитории превращаются в прокладку над `Session`** → принимаем: репозиторий содержит только запросы и ни одного правила; выигрыш в том, что SQL уходит из сервисов.
- **Один `Session` на запрос** (FastAPI кэширует `Depends` в пределах запроса) → `get_current_user` и сервисы делят сессию, поэтому `commit` в сервисе виден всем ниже по стеку. Следствие: коммитить только в конце операции и не оставлять незавершённых изменений.
- **Циклический импорт между `dependencies/` и `services/`** → сервисы не импортируют `dependencies`; зависимости идут только в одну сторону, `__init__.py` пустой.
- **`dependencies/services.py` разрастётся** → на текущих двух доменах это ~20 строк; делить по доменам имеет смысл после примерно десяти провайдеров.

## Migration Plan

Порядок шагов оставляет приложение запускаемым после каждого:

1. `services/storage.py` — чистый вынос функций, импорты обновляются на месте.
2. `repositories/` — новый слой, старый код ещё используется.
3. Сервисы → классы с репозиториями; `db.commit` концентрируется в сервисах.
4. `dependencies/` — провайдеры и алиасы.
5. Роутеры на алиасы, удаление `app/api/deps.py`.
6. `AGENTS.md` — карта репозитория.
7. Прогон девяти обращений и сверка кодов.

Откат — реверт коммитов change: изменений схемы БД нет, данные не затрагиваются, файлы на диске не переезжают.
