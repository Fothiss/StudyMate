# Design

## Context

Мотивация — в `proposal.md`. Опоры и ограничения:

- Слои и DI появились в `backend-layered-architecture`: репозиторий не коммитит, транзакцией владеет сервис, зависимости собираются в `app/dependencies/`.
- В БД уже есть `users` и `materials`; локально это SQLite, схема создаётся `Base.metadata.create_all` при старте, миграций нет.
- `docs/sql_scripts.sql` описывает исходную схему «классная комната», `docs/er.md` — упрощения solo-сценария: `assignments` + `results` слиты в `attempts`, `teacher_id` → `user_id`, поля проверки учителем убраны.
- `POST /quiz/check` сейчас принимает от клиента и вопрос, и эталон (`OpenAnswer.reference`), а GigaChat вызывается модульными функциями `services/gigachat.py` — без точки подмены для тестов.
- Фронтенд в этом change не меняется и продолжает считать тестовые вопросы локально по `correct_index`.

## Goals / Non-Goals

**Goals:**

- Тест, вопросы, варианты, эталоны, попытки и ответы живут в БД.
- Тестовые вопросы оцениваются на сервере по сохранённым данным.
- Открытые ответы оцениваются по эталонам **из БД**.
- У generation-эндпоинта точка подмены модели для тестов.
- Первые автоматические тесты в проекте.

**Non-Goals:**

- Правки фронтенда и удаление `POST /quiz/check` (следующий change).
- Скрытие `correct_index` и `reference` из ответа при прохождении.
- Единый итоговый балл, веса вопросов, фоновые задачи, Alembic.
- Удаление материалов и очистка старых тестов.

## Decisions

**1. Таблицы ближе к `er.md`, чем к `sql_scripts.sql`.**

`attempts` вместо `assignments` + `results`; нет `user_role`, `graded_by`, `teacher_score`, `teacher_comment`. Типы переносимые: `VARCHAR(36)` для ключей, `JSON` для `summary` и `generation_params`, `DATETIME`, `NUMERIC`. Альтернатива — взять `sql_scripts.sql` буквально — принесла бы ENUM-типы и `gen_random_uuid()`, несовместимые с SQLite, и половину полей, которые в solo-сценарии не заполняются никогда.

**2. Словарь типов вопросов — `choice` / `open`, а не `closed` / `open`.**

`choice` уже используется в схеме ответа модели и в фронтенде; второй словарь (`closed`) завёл бы перевод там, где он не нужен.

**3. `tests.summary` — колонка `JSON`, которой нет в исходном скрипте.**

Без неё краткое содержание теряется при перезагрузке: сейчас оно приходит в ответе генерации и живёт только в `sessionStorage`.

**4. Убрать `CHECK (answer_text IS NOT NULL OR selected_option_id IS NOT NULL)`.**

Неотвеченный тестовый вопрос — легальное состояние (`web-quiz` требует принимать такую сдачу), а обе колонки у него `NULL`. Ограничение отвергало бы валидный сценарий.

**5. Сдача в два шага: `POST /tests/{id}/attempts`, затем `POST /attempts/{id}/check`.**

Первый шаг без модели — отвечает сразу. Второй — LLM, до 120 секунд. Альтернатива «один `submit` со всем» заставила бы ждать две минуты даже ради результата по тестовым вопросам и сломала бы сценарий «проверка открытых в процессе» из `web-quiz`.

**6. Тестовые вопросы оцениваются по `closed_question_options.is_correct` в БД.**

Не по `correct_index` из клиентского запроса — иначе оценку можно подделать. Это же готовит почву для change 2, где `correct_index` перестанет уходить клиенту.

**7. Эталоны для проверки берутся из `open_question_rubrics`, а не из тела запроса.**

Сейчас клиент сам присылает `reference`, то есть может подставить выгодный эталон и получить завышенный балл. Новый эндпоинт читает эталон из БД по `question_id`.

**8. Общая точка подмены модели: `services/ai.py` + провайдер в DI.**

`services/gigachat.py` остаётся транспортом (OAuth, `with_structured_output`, обработка ошибок), а `ai.py` даёт сервисам узкий интерфейс `generate_quiz(...)` / `evaluate_answers(...)`. В `app/dependencies/services.py` появляется `get_ai_service`/`AIServiceDep`, поэтому тесты подменяют модель через `app.dependency_overrides`, а не monkeypatch. В `backend-layered-architecture` это было отложено до момента, когда подмена реально понадобится — она понадобилась здесь, на первых тестах.

**9. Генерация остаётся обратно совместимой.**

`POST /materials/{id}/quiz` добавляет `test_id`, но сохраняет `summary` и `questions` вместе с `correct_index` и `reference`. Иначе текущий UI перестал бы работать, а правки фронтенда — это change 2. Конвертер `Quiz` → строки живёт в `services/quiz_storage.py`, ответ API описывает отдельная схема `TestRead`; контракт модели и контракт API не смешиваются.

**10. Одна строка `answers` на каждый вопрос при создании попытки.**

Неотвеченные сохраняются как `NULL` в обеих колонках. Так работает `UNIQUE(attempt_id, question_id)`, разбор попытки не требует «дополнить недостающие» и подсчёт остаётся циклом по вопросам теста.

**11. `final_score` заполняться не будет.**

В `attempts` хранятся `choice_correct` и `choice_total`; по открытым — `llm_score` в каждой строке `answers`. Единая формула смешивания шкалы «0–100 у открытых» и «верно/всего у тестовых» была бы выдумкой, которую пришлось бы переделывать.

**12. `POST /quiz/check` сохраняется как устаревший.**

Удаление сломает текущий UI. Оба эндпоинта вызывают один и тот же код проверки, чтобы не разъезжаться; удаление — в change 2.

**13. Тесты — `pytest` + `httpx.TestClient`.**

БД подменяется через `dependency_overrides` на `get_db` с временным файлом SQLite (не `:memory:`: `Session` из другого потока `TestClient` иначе не увидит таблицы). Модель подменяется через `AIServiceDep`.

## Risks / Trade-offs

- **Каждая генерация создаёт новую строку `tests`** → таблица растёт без очистки. Пока принимаем: история попыток требует неизменных вопросов, а старые тесты удаляются вместе с материалом через `ON DELETE CASCADE`. Отдельная задача очистки не входит в change.
- **Эндпоинты попыток не используются UI до change 2** → покрываются тестами в этом же change; без них сдача непроверенного API недопустима.
- **Две ветки проверки открытых ответов живут одновременно** → обе идут через один код сервиса; удаление `/quiz/check` запланировано в change 2.
- **SQLite возвращает `NUMERIC` как float** → храним два знака, в тестах сравниваем с допуском, а не на точное равенство.
- **Сдача без последующей проверки оставляет попытку в статусе `submitted`** → это штатное состояние, разбор попытки показывает открытые ответы как непроверенные, а `POST /attempts/{id}/check` можно вызвать позже.
- **Нет Alembic** → добавление таблиц переживается `create_all`, но последующее переименование колонок потребует миграций; сейчас таких планов нет.

## Migration Plan

1. Модели и регистрация в `app/models/__init__.py` — `create_all` добавит таблицы при старте, существующие `users` и `materials` не затрагиваются.
2. Тестовая инфраструктура (`pytest`, фикстуры, подмена `get_db` и `AIServiceDep`).
3. Репозитории и провайдеры `tests`/`attempts`.
4. Сохранение теста при генерации и `test_id` в ответе.
5. Создание попытки с серверной оценкой тестовых вопросов.
6. Проверка открытых ответов по эталонам из БД.
7. Чтение истории и разбора попытки.
8. `docs/er.md` в соответствие с фактическими таблицами.

Откат: удалить новые таблицы (или файл локальной базы) — данные `users` и `materials` не мигрируют, файлы на диске не переезжают. Единственное изменение существующего контракта — лишнее поле `test_id` в ответе генерации, которое старый клиент игнорирует.
