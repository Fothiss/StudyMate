# Design

## Context

Мотивация — в `proposal.md`. Состояние, из которого исходим:

- `persist-quizzes-and-attempts` добавил `POST /tests/{id}/attempts`, `POST /attempts/{id}/check`, `GET /attempts`, `GET /attempts/{id}`; сервер уже оценивает тестовые вопросы по БД и проверяет открытые по эталонам из БД.
- Клиент по-прежнему считает тестовые вопросы сам (`answers[i] === correct_index`) в `components/practice/practice-result.tsx`, хранит тест, ответы и результат в `sessionStorage` (`lib/practice-storage.ts`) и проверяет открытые через устаревший `POST /quiz/check` с эталоном из тела запроса.
- `web-quiz` сейчас требует хранить результат в `sessionStorage` — это требование меняется.
- Роутинг: `/` и `/quiz` внутри `RequireAuth` + `AppShell`; страница результатов добавляется туда же.

## Goals / Non-Goals

**Goals:**

- Единственный источник истины по результату — сохранённая попытка.
- Клиент физически не получает правильные ответы до сдачи.
- Разбор попытки доступен по ссылке, после перезагрузки и позже из истории.
- Один компонент разбора вместо двух.

**Non-Goals:**

- Изменения схемы БД, новые эндпоинты статистики, пагинация истории.
- Удаление попыток и материалов, экспорт, работа офлайн.
- Сохранение черновика между вкладками или на сервере.

## Decisions

**1. Сдача остаётся двухшаговой, как в `persist-quizzes-and-attempts`.**

`POST /tests/{id}/attempts` возвращает сразу, `POST /attempts/{id}/check` — до 120 секунд. Это сохраняет нынешний UX: результат по тестовым виден мгновенно, открытые догружаются отдельно. Альтернатива «один запрос на всё» заставила бы ждать две минуты и потеряла бы сценарий «проверка в процессе».

**2. Ответ генерации перестаёт содержать `correct_index` и `reference`.**

Пока они приходят клиенту, «скрытые ответы» остаются декорацией: их видно в devtools. Сервер уже умеет оценивать без них. Альтернатива «оставить в payload, но не показывать» — это ровно текущее состояние, ради исправления которого делается change.

**3. `POST /quiz/check` удаляется.**

Два пути проверки открытых ответов разъезжаются в поведении, а старый вдобавок доверяет эталону из запроса. После перевода UI остаётся один путь — `POST /attempts/{id}/check`.

**4. В `sessionStorage` остаётся только черновик прохождения.**

Хранятся `test_id`, данные ответы и текущий вопрос; результат — никогда. Ключ меняется на `studymate:practice:v2`, старый черновик версии 1 отбрасывается: в нём нет `test_id`, и продолжить его нельзя. Альтернатива «хранить и результат» даёт два источника истины и расхождение после перезагрузки.

**5. Разбор попытки — отдельный маршрут `/results/:attemptId`, и он же — экран результата практики.**

После создания попытки практика переходит на этот маршрут. Тогда разбор существует в одном экземпляре: `practice-result.tsx` перестаёт быть отдельной реализацией результата и заменяется компонентом разбора. Альтернатива «оставить два похожих экрана» — двойная поддержка одной и той же вёрстки.

**6. Проверку открытых инициирует страница разбора, а не экран практики.**

Нормальный разбор показывает уже сохранённые оценки и не дёргает модель. Исключение — переход сразу после сдачи: практика передаёт признак в состоянии навигации, и страница один раз запускает проверку. Защита от повторного запуска — ref, потому что строгий режим React монтирует компонент дважды. Альтернатива «всегда проверять при открытии» тратила бы запрос к модели на каждый просмотр истории.

**7. Сводка прогресса считается на клиенте из списка попыток.**

`GET /attempts` уже отдаёт материал и счёт, поэтому отдельный эндпоинт статистики не нужен. Дашборд берёт первые три попытки срезом на клиенте, а не новым параметром `limit`: история пока мала, а лишний параметр пришлось бы поддерживать в контракте. Когда история вырастет, пагинация станет отдельной задачей.

**8. Порядок правок обратный очевидному.**

Сначала UI начинает пользоваться эндпоинтами попыток, и только потом сервер перестаёт отдавать ответы и удаляет `/quiz/check`. В обратном порядке приложение ломается посередине change.

**9. Пустые и неотвеченные вопросы показываются явно.**

Разбор не пропускает вопросы без ответа и не подставляет «нулевой балл» там, где модель не вызывалась: неотвеченный вопрос показывается как «не отвечен», непроверенный открытый — как «не проверен» с кнопкой.

## Risks / Trade-offs

- **Удаление `correct_index` ломает любого другого потребителя ответа генерации** → сейчас потребитель один, `frontend/`; правка идёт в том же change, контракт проверяется тестом.
- **Порядок «сначала UI, потом удаление» оставляет короткое окно с двумя путями проверки** → в окне оба пути ведут в один сервис, поэтому поведение не расходится.
- **Страница разбора может запустить проверку дважды** → запуск помечается ref, а повторный запрос всё равно перезаписывает оценки теми же значениями.
- **Черновик версии 1 теряется при обновлении** → это осознанно: в нём нет `test_id`, продолжить такое прохождение невозможно.
- **Дашборд запрашивает весь список попыток ради трёх строк** → принимаем до появления пагинации.
- **`GET /attempts/{id}` возвращает эталоны, то есть правильные ответы** → это допустимо только после сдачи: эндпоинт отдаёт данные сохранённой попытки, а не теста до прохождения.

## Migration Plan

1. Типы и функции API-клиента для попыток.
2. Компонент разбора и маршрут `/results/:attemptId`.
3. Перевод практики на `POST /tests/{id}/attempts` и переход на маршрут разбора; удаление локального сравнения и `practice-evaluate.ts`.
4. Страница истории `/results`, пункт навигации, раздел «Результаты» на дашборде.
5. Черновик версии 2: только `test_id`, ответы и текущий вопрос.
6. Сервер: убрать `correct_index`/`reference` из ответа генерации, удалить `POST /quiz/check` и его схему.
7. Проверка: полный сценарий, перезагрузка в середине прохождения, открытие попытки по прямой ссылке.

Откат: реверт коммитов. Схема БД не меняется, сохранённые попытки остаются читаемыми. Откат шага 6 в отдельности невозможен без возврата `correct_index` в ответ — поэтому шаг 6 идёт последним и отдельным коммитом.

## Open Questions

- Пагинация истории и ограничение `GET /attempts` — отдельная задача, когда попыток станет много; на текущий контракт и задачи не влияет.
